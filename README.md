# Форма регистрации — учебный проект

Проект для практического семинара по поиску и исправлению ошибок. Участники исследуют форму регистрации на «импровизированном проде», восстанавливают требования через диалог с преподавателем и оформляют исправления в Git.

Форма содержит поля телефона, пароля и подтверждения пароля, индикатор надёжности и кнопку регистрации. Проект написан на HTML, CSS и JavaScript без фреймворков и сборки.

> Это учебная демонстрация: серверной части и создания учётных записей нет. Сообщение об успешной регистрации показывает результат клиентской проверки.

## Цель занятия

Научиться замечать ошибочное поведение, формулировать проверяемые гипотезы, уточнять требования у заказчика и вносить обоснованные исправления.

Итоговые требования:

- Телефон принимается только в формате `+7XXXXXXXXXX`: знак `+`, код страны `7` и ровно 10 цифр после него.
- Пароль считается безопасным только при выполнении согласованных критериев надёжности.

Точные критерии пароля и остальные детали поведения нужно уточнить у преподавателя. Текущая реализация, подсказки и индикатор надёжности могут содержать ошибки и не являются источником требований.

## Запуск

1. Склонируйте репозиторий:

   ```bash
   git clone https://github.com/oastolyarov/registration-form.git
   cd registration-form
   ```

2. Если преподаватель назначил стартовую ветку, переключитесь на неё:

   ```bash
   git switch <стартовая-ветка>
   ```

3. Откройте файл `index.html` в браузере.

Установка зависимостей, Node.js и локальный сервер не требуются. В командах заменяйте значения в угловых скобках на свои, не сохраняя сами скобки.

## Порядок работы на семинаре

### 1. Исследуйте форму

Проверьте разные варианты ввода и найдите нелогичное поведение. Обратите внимание на сообщения об ошибках, оценку надёжности пароля и доступность кнопки регистрации.

Для каждого наблюдения запишите входные данные, последовательность действий и фактический результат.

### 2. Сформулируйте гипотезу и уточните требования

Обсудите наблюдения в группе и задайте преподавателю вопросы. Он выступает экспертом-заказчиком и может подтвердить или опровергнуть гипотезу.

До изменения кода зафиксируйте:

- какое поведение ошибочно;
- каким должен быть правильный результат;
- какие примеры должны проходить проверку, а какие — отклоняться.

Не подменяйте согласование требований собственными предположениями.

### 3. Исправьте ошибку

Создайте рабочую ветку от назначенной стартовой ветки:

```bash
git switch -c fix/<краткое-описание>
```

Внесите изменения по согласованному требованию. Можно писать код самостоятельно или использовать AI-инструменты; ответственность за результат и его проверку остаётся у команды.

### 4. Проверьте результат

Повторите исходный сценарий воспроизведения и проверьте допустимые, недопустимые и граничные значения. Убедитесь, что сообщения, индикатор надёжности и кнопка регистрации согласованы с результатом проверки.

Автоматические тесты в проекте не настроены. Зафиксируйте результаты ручной проверки в описании запроса на слияние.

### 5. Создайте коммит и запрос на слияние

Просмотрите изменения и добавьте в коммит только файлы своего исправления:

```bash
git diff
git add <изменённый-файл>
git commit -m "fix: <описание исправления>"
git push -u origin HEAD
```

Откройте запрос на слияние из своей рабочей ветки в целевую ветку, указанную преподавателем. В GitHub он называется **Pull Request (PR)**, в GitLab — **Merge Request (MR)**.

В описании укажите:

- **Проблема:** шаги воспроизведения и фактический результат.
- **Требование:** ожидаемое поведение, подтверждённое преподавателем.
- **Исправление:** что изменено и почему.
- **Проверка:** примеры входных данных, ожидаемые и полученные результаты.

## Критерии завершения

- Ошибка воспроизведена и описана.
- Ожидаемое поведение согласовано с преподавателем.
- Исправление проверено на допустимых, недопустимых и граничных значениях.
- Изменения закоммичены и отправлены в рабочую ветку.
- PR или MR открыт в согласованную целевую ветку и содержит результаты проверки.
